\section{Part 1: Why This Matters}

\begin{frame}{The LLM era, in numbers}
  \begin{columns}[T]
    \column{0.55\textwidth}
      \begin{block}{Model size has grown $\sim$1000$\times$ in 5 years}
        \begin{itemize}
          \item GPT-2 (2019): \textbf{1.5\,B} parameters
          \item GPT-3 (2020): \textbf{175\,B}
          \item PaLM (2022): \textbf{540\,B}
          \item GPT-4 (2023, est.): \textbf{$\sim$1.7\,T}
          \item Frontier models 2025: trillions, mixture-of-experts
        \end{itemize}
      \end{block}
      \begin{watchout}
        Both training \emph{and} serving are GPU-bound:
        \begin{itemize}
          \item GPT-3 training: $\sim$\$5\,M of compute
          \item GPT-4 training: $\sim$\$100\,M
          \item ChatGPT serving: $\sim$\$700\,K\,/\,day (2023 est.)
          \item $> 90\%$ of those dollars are \textbf{GPU hours}
        \end{itemize}
      \end{watchout}
    \column{0.45\textwidth}
      \begin{aha}
        Every LLM dollar is a GPU cycle. Cycles get spent inside a
        small set of operations: matmuls, attention, normalisations,
        activations, KV-cache I/O.\\[6pt]
        Of these, \textbf{attention scales worst with context length} --
        and context length is the axis everyone is racing on.
      \end{aha}
      \vspace{0.4em}
      {\small\itshape Shave 30\,\% off the attention kernel and you
      shave a measurable fraction off the cost of \emph{running the
      whole model}.}
  \end{columns}
\end{frame}

\begin{frame}{Where do the GPU cycles actually go?}
  \begin{columns}[T]
    \column{0.5\textwidth}
      \begin{block}{Forward-pass cost breakdown (per transformer block)}
        \begin{itemize}
          \item \textbf{Linear projections} (Q, K, V, output, MLP):\\
                cost is $O(N \cdot D^2)$ -- linear in $N$.
          \item \textbf{Attention} ($Q K^\top$, softmax, $P V$):\\
                cost is $O(N^2 \cdot D)$ -- \textbf{quadratic in $N$}.
          \item \textbf{LayerNorm, activations}: small, often fused.
          \item \textbf{KV-cache I/O} (decode): bandwidth-bound, scales
                with $N$.
        \end{itemize}
      \end{block}
    \column{0.5\textwidth}
      \begin{spoiler}
        For short prompts ($N \lesssim 2048$) the linear projections
        dominate. As $N$ grows, attention takes over -- because it
        grows as $N^2$ while everything else grows as $N$.\\[4pt]
        At $N = 32{,}768$ (GPT-4 default) attention is the
        \emph{single largest} kernel in the forward pass on a typical
        decoder.
      \end{spoiler}
      \vspace{0.4em}
      \textbf{Why this matters for us.} Models are racing toward 128K,
      1M, 10M context windows. Attention's share of cost grows
      monotonically with that race. \emph{Every vendor invests heavily
      here.}
  \end{columns}
\end{frame}

\begin{frame}{Attention, the mechanism in one slide}
  \begin{block}{The operation that made transformers work}
    For each query token $q_i$, score it against every key $k_j$, run
    a softmax over those scores, then use the resulting weights to mix
    the values $v_j$. The output for position $i$ is a weighted sum
    over all values.
  \end{block}
  \[
    \mathrm{Attention}(Q, K, V) =
    \mathrm{softmax}\!\left(\tfrac{Q K^\top}{\sqrt{D}}\right) V.
  \]
  \begin{columns}[T]
    \column{0.55\textwidth}
      \begin{itemize}
        \item $Q, K, V$: $N \times D$ matrices ($N$\,=\,sequence length,
              $D$\,=\,head dim).
        \item $S = Q K^\top$: $N \times N$ -- the score matrix; here
              the quadratic cost lives.
        \item Softmax is row-wise: each query distributes attention
              probability over all keys.
        \item $P V$: gives the output $O$, again $N \times D$.
      \end{itemize}
    \column{0.45\textwidth}
      \begin{aha}
        \emph{``Each token reads every other token, decides how much
        it cares about each one, and pulls a weighted summary of
        their values back to itself.''}\\[4pt]
        That all-to-all structure is exactly what makes attention
        powerful \emph{and} what makes it expensive.
      \end{aha}
  \end{columns}
\end{frame}

\begin{frame}{Why attention is hard on hardware}
  \textbf{Two distinct problems, both rooted in the $N{\times}N$ score matrix.}
  \vspace{0.3em}
  \begin{columns}[T]
    \column{0.5\textwidth}
      \begin{watchout}
        \textbf{Problem 1 -- memory bandwidth.}\\[2pt]
        $S$ and $P$ are each $N{\times}N$ per (batch, head). At
        $N = 8192$, batch $2$, heads $8$, FP32 that's
        $\approx 4.3$\,GB \emph{per intermediate}. Reading and writing
        them through HBM at $\sim 960$\,GB/s is the bottleneck -- not
        the arithmetic.
      \end{watchout}
    \column{0.5\textwidth}
      \begin{watchout}
        \textbf{Problem 2 -- arithmetic throughput.}\\[2pt]
        The two matmuls dominate FLOPs. They run fast \emph{only if}
        data is in the right precision, the right layout, on the right
        units (Tensor Cores). FP32 ALU is $\sim 50\times$ slower than
        FP16 Tensor Cores; FP16 is $2\times$ slower than FP8; FP8 is
        $2\times$ slower than FP4.
      \end{watchout}
  \end{columns}
  \vspace{0.5em}
  \begin{aha}
    \textbf{Two levers, then.} Avoid materialising $S$ and $P$
    (\emph{memory lever}), and use the narrowest precision Tensor Cores
    you can while keeping the output usable (\emph{compute lever}).
    Our work measures both, in isolation, on the RTX\,5080.
  \end{aha}
\end{frame}

\section{Part 2: What the Field Has Done}

\begin{frame}{Two parallel research threads}
  \begin{columns}[T]
    \column{0.5\textwidth}
      \begin{block}{Thread A -- algorithmic fusion}
        Restructure the computation so $S$ and $P$ \emph{never} live in
        HBM. Same precision, less memory traffic.
        \begin{itemize}
          \item 2018 -- Online softmax (Milakov \& Gimelshein).
          \item \textbf{2022 -- FlashAttention} (Dao et al., A100).
          \item 2023 -- FlashAttention-2 (better partitioning).
          \item 2024 -- FlashAttention-3 (Hopper, TMA, FP8).
        \end{itemize}
      \end{block}
    \column{0.5\textwidth}
      \begin{block}{Thread B -- lower precision}
        Carry the same computation in narrower data types so each
        Tensor-Core instruction does more work per cycle.
        \begin{itemize}
          \item 2017 -- FP16 mixed precision (Micikevicius).
          \item \textbf{2022 -- FP8 formats} (Micikevicius, NVIDIA).
          \item 2024 -- FP8 attention deployed (FA-3, SageAttention).
          \item \textbf{2025 -- NVFP4 attention} (SageAttention3, RTX\,5090).
        \end{itemize}
      \end{block}
  \end{columns}
  \vspace{0.4em}
  \begin{tldr}
    These threads are \emph{multiplicative}, not exclusive. A modern
    optimised attention kernel applies fusion \textbf{and} narrow
    precision. Our ladder isolates the contribution of each thread on
    a hardware tier where neither has been characterised.
  \end{tldr}
\end{frame}

\begin{frame}{Consumer Blackwell, in numbers}
  \begin{columns}[T]
    \column{0.5\textwidth}
      \begin{block}{NVIDIA GeForce RTX\,5080 (our card)}
        \begin{itemize}
          \item Architecture: \textbf{Blackwell, sm\_120a}
          \item \textbf{84} streaming multiprocessors (SMs)
          \item \textbf{16\,GB} GDDR7, $\approx 960$\,GB/s HBM
          \item 5\textsuperscript{th}-generation Tensor Cores
          \item Native FP8 (E4M3 / E5M2) \textbf{and} FP4 (NVFP4)
          \item 256-bit memory bus
          \item Released early 2025
        \end{itemize}
      \end{block}
    \column{0.5\textwidth}
      \begin{aha}
        \textbf{What it shares with datacenter Blackwell:} same MMA
        instruction families, same FP8 / FP4 formats, the same NVFP4
        hardware support \emph{in principle}.
      \end{aha}
      \begin{whatbroke}
        \textbf{What it lacks (and why this hurts):}
        \begin{itemize}
          \item No \textbf{TMA} (Tensor Memory Accelerator) -- so
                FA-3's warp-specialised pipeline does not transfer.
          \item CUTLASS \texttt{77\_blackwell\_fmha} reference is
                gated to \texttt{sm\_100a} / \texttt{sm\_103a}.
          \item Hardware NVFP4 path requires swizzled SMEM layouts.
        \end{itemize}
      \end{whatbroke}
  \end{columns}
\end{frame}

\begin{frame}{Tensor Cores: three precisions, three throughputs}
  Same MMA instruction family, three precisions. The kernel selects
  one explicitly via inline PTX or via the high-level
  \texttt{nvcuda::wmma} API.
  \vspace{0.4em}
  \begin{center}
  \begin{tabular}{l l l c c}
    \toprule
    \textbf{Precision} & \textbf{Mnemonic} & \textbf{Shape} & \textbf{Used by} & \textbf{Theory} \\
    \midrule
    FP16 (E5M10) & \texttt{HMMA.16816.F32} & $16{\times}8{\times}16$ & V1, V2 (\texttt{wmma}) & $1\times$ \\
    FP8 (E4M3)   & \texttt{QMMA.16832.F32.E4M3.E4M3} & $16{\times}8{\times}32$ & V3 (inline PTX) & $2\times$ \\
    FP4 (E2M1)   & \texttt{QMMA.16832.F32.E2M1.E2M1} & $16{\times}8{\times}32$ & V4 (inline PTX) & $4\times$ \\
    \bottomrule
  \end{tabular}
  \end{center}
  \vspace{0.4em}
  \begin{itemize}
    \item \textbf{HMMA = ``Half MMA''} -- FP16 inputs, FP32 accumulator.
    \item \textbf{QMMA = ``Quarter MMA''} on consumer Blackwell SASS;
          covers FP8 \emph{and} FP4 (precision encoded in the suffix).
    \item Each instruction uses a per-thread \emph{fragment} layout
          fixed by the PTX ISA. You load operands into registers, call
          the instruction, read the accumulator.
    \item FP4 specifically requires \texttt{sm\_120a}, not plain
          \texttt{sm\_120}.
  \end{itemize}
\end{frame}

\begin{frame}{What FP8 and FP4 can actually represent}
  \begin{columns}[T]
    \column{0.5\textwidth}
      \begin{block}{FP8 (E4M3)}
        \begin{itemize}
          \item 1 sign + 4 exponent + 3 mantissa bits
          \item Max representable magnitude: \textbf{448}
          \item $\sim 16$ representable positive values
          \item Reasonable for unscaled inputs around 1
        \end{itemize}
      \end{block}
    \column{0.5\textwidth}
      \begin{watchout}
        \textbf{FP4 (E2M1) -- yes really, only this many values:}
        \begin{itemize}
          \item 1 sign + 2 exponent + 1 mantissa bit
          \item Representable positives:
                \textbf{\{0, 0.5, 1, 1.5, 2, 3, 4, 6\}}
          \item Max magnitude: \textbf{6}
          \item \textbf{Useless without per-block rescaling.}
        \end{itemize}
      \end{watchout}
  \end{columns}
  \vspace{0.5em}
  \begin{aha}
    \textbf{Microscaling, in plain language.} Real activation tensors
    span many orders of magnitude. They will not fit into FP8 (let
    alone FP4) directly. \emph{The trick:} divide each block (a tile,
    a row, or a small group of elements) by its own absmax, store the
    small-range result, multiply by the saved scale when reading back.
    The Tensor-Core instruction operates on the small-range data; the
    scales live in FP32 and apply at the accumulator.
  \end{aha}
\end{frame}

\begin{frame}{V0: FP32 naive -- the oracle}
  \begin{columns}[T]
    \column{0.55\textwidth}
      \textbf{Motivation.} We need a deliberately-slow but
      \emph{transparently correct} baseline. Every other variant is
      checked against this kernel's output -- without an oracle there
      is no way to claim a numerical regression.
      \vspace{0.4em}
      \begin{whatif}
        \begin{itemize}
          \item Three separate kernel launches: $Q K^\top$, then
                row-wise softmax, then $P V$.
          \item All FP32; no Tensor Cores.
          \item Materialises full $S$ and $P$ in HBM.
        \end{itemize}
      \end{whatif}
      \begin{whatbroke}
        Softmax row-reduce needs \texttt{\_\_syncthreads()}
        \emph{between} max-reduce and sum-reduce. Without it: a fast
        warp overwrites the shared row-max while a slow warp is still
        reading it. \textbf{6\% nondeterministic mismatch on large
        $N$ -- hours to find.}
      \end{whatbroke}
    \column{0.45\textwidth}
      \begin{numbers}
        \textbf{$N = 2048$, $D = 128$:}
        \begin{itemize}
          \item Latency: \textbf{4{,}500} ms
          \item Memory: \textbf{640} MB
          \item Tensor-Core insns: \textbf{0}
          \item Rel L2 vs FP32: \textbf{0} (it is the reference)
          \item OOM past $N \approx 2048$
        \end{itemize}
      \end{numbers}
      \begin{aha}
        \textbf{Take-away:} naive attention is unworkable past tiny
        $N$. Optimisation isn't optional.
      \end{aha}
  \end{columns}
\end{frame}

\begin{frame}{V1: FP16 tiled with WMMA Tensor Cores}
  \begin{columns}[T]
    \column{0.6\textwidth}
      \textbf{Motivation.} Isolate the contribution of \emph{Tensor
      Cores + tiling} before changing anything else. Keep V0's
      three-launch structure deliberately, so the V1$\to$V2 step later
      cleanly measures fusion.
      \vspace{0.4em}
      \begin{whatif}
        \begin{itemize}
          \item Inputs in FP16; FP32 accumulators.
          \item Both matmuls go through \texttt{nvcuda::wmma} -- compiles
                to \texttt{HMMA.16816.F32}.
          \item \textbf{Trick \#1:} get $K^\top$ for free by loading $K$
                as \texttt{matrix\_b col\_major}. Same memory,
                transposed in operand-space.
          \item \textbf{Trick \#2:} all SMEM in a single dynamic
                allocation. Static + dynamic together hit the 48\,KB
                per-block default cap at $D = 128$ -- raise it via
                \texttt{cudaFuncSetAttribute}.
          \item Still materialises $S$ and $P$ in HBM (V2's problem).
        \end{itemize}
      \end{whatif}
    \column{0.4\textwidth}
      \begin{numbers}
        \textbf{$N = 8192$, $D = 128$:}
        \begin{itemize}
          \item Latency: \textbf{77.1} ms
          \item Memory: \textbf{2176} MB
          \item HMMA insns: \textbf{120 + 32}
          \item Rel L2: $6 \times 10^{-4}$
        \end{itemize}
        \emph{$\sim 60\times$ faster than V0 already}, just from
        Tensor Cores. But still allocates 2\,GB.
      \end{numbers}
  \end{columns}
\end{frame}

\begin{frame}{V2: FP16 fused -- the FlashAttention idea}
  \begin{block}{Motivation -- pull the memory lever}
    Intermediates $S$ and $P$ are what makes V1 allocate gigabytes.
    \textbf{FlashAttention's idea}: process keys / values in tiles,
    keep a running per-row max and denominator, never materialise the
    full $S$ or $P$. \emph{Same precision, smaller HBM footprint.}
  \end{block}
  \[
    \alpha^{(t)} = \exp\bigl(m^{(t-1)} - m^{(t)}\bigr),\quad
    O^{(t)} = \alpha^{(t)}\, O^{(t-1)} + \tilde P^{(t)} V^{(t)}.
  \]
  \begin{columns}[T]
    \column{0.55\textwidth}
      \begin{whatif}
        \begin{itemize}
          \item One fused kernel; one block per output row-tile.
          \item Per-block SMEM at $D = 128$ totals \textbf{96\,KB},
                twice the default.
          \item Two boundary cases not in the FA paper but required:
                first iteration ($m = -\infty$), fully-masked rows.
                Both produce NaN otherwise.
          \item \textbf{No precision change.} The win is purely
                structural.
        \end{itemize}
      \end{whatif}
    \column{0.45\textwidth}
      \begin{numbers}
        \textbf{The 17$\times$ memory finding} ($N = 8192$, $D = 128$):
        \begin{center}
          \textbf{V1 = 2176\,MB} $\to$ \textbf{V2 = 128\,MB}
        \end{center}
        Same FP16 contract, no precision change. The full $N{\times}N$
        $S, P$ never appear in HBM.
      \end{numbers}
      {\small\itshape Latency improves modestly (60.9\,ms vs 77.1\,ms);
      the big win is that we can now run $N = 16{,}384$ on a 16\,GB
      card at all.}
  \end{columns}
\end{frame}

\begin{frame}{V3: FP8 fused with hand-rolled \texttt{mma.sync}}
  \begin{block}{Motivation -- pull the compute lever, twice}
    Two contributions, both unlocked by writing inline PTX instead of
    using the \texttt{wmma} API: \textbf{FP8 mma throughput} (theoretical
    $2\times$ FP16) and a \textbf{register-resident output accumulator}
    (V2 round-tripped $O$ through SMEM because WMMA fragment layout is
    implementation-defined; PTX layout is fully specified).
  \end{block}
  \begin{columns}[T]
    \column{0.6\textwidth}
      \begin{whatif}
        \begin{itemize}
          \item FP8 (E4M3) on Q, K, V, P. Inputs come in as FP16,
                quantised in-kernel.
          \item Per-tile FP8 scaling: $\mathrm{scale} = \max(|x|)/448$
                (Micikevicius 2022 recipe).
          \item \texttt{mma.sync.aligned.m16n8k32.row.col.f32.e4m3.e4m3.f32}
                via inline PTX.
          \item \textbf{Why not CUTLASS?} Its FMHA reference example is
                gated to \texttt{sm\_100a} / \texttt{sm\_103a}. No FMHA
                reference for consumer Blackwell exists.
        \end{itemize}
      \end{whatif}
    \column{0.4\textwidth}
      \begin{numbers}
        \textbf{$N = 8192$, $D = 128$:}
        \begin{itemize}
          \item Latency: \textbf{25.8} ms (\textbf{2.4$\times$} V2)
          \item Memory: \textbf{128} MB (same as V2)
          \item QMMA insns: \textbf{96}
          \item Rel L2: $5 \times 10^{-2}$
        \end{itemize}
      \end{numbers}
      \begin{aha}
        FP8 mma + register-resident O.\\
        Both unlocked by \emph{the layout becoming knowable}.
      \end{aha}
  \end{columns}
\end{frame}

\begin{frame}{V4: NVFP4 with software microscaling -- the negative result}
  \begin{block}{Motivation -- one more compute lever}
    FP4 promises another $2\times$ over FP8. SageAttention3 has
    demonstrated this on RTX\,5090 via the \emph{hardware-microscaled}
    \texttt{mxf4nvf4.m16n8k64} mma. \textbf{Does this transfer to
    RTX\,5080?}
  \end{block}
  \begin{columns}[T]
    \column{0.6\textwidth}
      \begin{whatif}
        \begin{itemize}
          \item Same V3 skeleton, but FP4 (E2M1) instead of FP8.
          \item \texttt{kind::f8f6f4.m16n8k32} -- the
                \emph{software-microscaled} path. FP4 packed in the
                middle 4 bits of each byte.
          \item Per-row, per-K-block (block size 32) FP32 scales,
                applied at the accumulator after every mma.
        \end{itemize}
      \end{whatif}
      \begin{whatbroke}
        Could not use \texttt{mxf4nvf4.m16n8k64}: its scattered-fragment
        layout requires \texttt{ldmatrix}-style swizzled SMEM,
        incompatible with V3's row-major SMEM idiom. Multi-week scope
        to port. Software path costs $\sim 12$ register ops per mma --
        $\sim 1100$ ops/thread/iter total.
      \end{whatbroke}
    \column{0.4\textwidth}
      \begin{numbers}
        \textbf{$N = 8192$, $D = 128$:}
        \begin{itemize}
          \item Latency: \textbf{33.4} ms\\
                ($\mathbf{0.77\times}$ V3 -- \emph{slower!})
          \item Memory: \textbf{128} MB
          \item QMMA insns: \textbf{96}
          \item Rel L2: $0.21$
        \end{itemize}
      \end{numbers}
      \begin{spoiler}
        Software-microscaling overhead $>$ FP4 throughput advantage.
        \textbf{This is a finding, not a failure.}
      \end{spoiler}
  \end{columns}
\end{frame}

\section{Part 5: Findings}

\begin{frame}{Finding 1 -- Memory wall breaks at V2}
  \begin{center}
    \includegraphics[width=0.6\linewidth]{../paper/figures/fig_memory_vs_seqlen.pdf}
  \end{center}
  \begin{itemize}
    \item V1 grows quadratically (full $N{\times}N$ in HBM); V2 grows
          linearly ($O(N \cdot D)$).
    \item At $N = 8192$, $D = 128$: V1 = \textbf{2176\,MB}, V2 =
          \textbf{128\,MB} $\Rightarrow$ \textbf{17$\times$ reduction}.
    \item V2, V3, V4 and SDPA all overlap on this plot.
  \end{itemize}
  \begin{aha}
    This is what makes long-context inference \emph{feasible} on a
    16\,GB consumer card. Without it, $N = 16{,}384$ at our
    $(\mathrm{batch}, \mathrm{heads}) = (2, 8)$ does not fit at all.
  \end{aha}
\end{frame}

\begin{frame}{Finding 2 -- V3 closes half the SDPA gap with FP8}
  \begin{columns}[T]
    \column{0.55\textwidth}
      \includegraphics[width=\linewidth]{../paper/figures/fig_latency_vs_seqlen.pdf}
    \column{0.45\textwidth}
      \begin{numbers}
        \textbf{$N = 8192$, $D = 128$:}
        \begin{itemize}
          \item V2: $\sim$60\,ms
          \item V3: $\sim$26\,ms (\textbf{2.4$\times$} V2)
          \item SDPA: $\sim$12\,ms
        \end{itemize}
      \end{numbers}
      \begin{aha}
        \textbf{Why V3 wins this much:}
        \begin{itemize}
          \item FP8 mma throughput
                ($\sim 2\times$ FP16)
          \item Register-resident O\\
                (V2 round-trips through SMEM)
        \end{itemize}
        Both unlocked by the same change: PTX-specified fragment
        layout.
      \end{aha}
  \end{columns}
\end{frame}

\begin{frame}{Finding 3 -- V4 is \emph{slower} than V3}
  \begin{center}
    \includegraphics[width=0.55\linewidth]{../paper/figures/fig_pareto_main.pdf}
  \end{center}
  \begin{itemize}
    \item V4 (red triangle) sits at \textbf{higher latency} \emph{and}
          \textbf{higher error} than V3 (orange diamond). Strictly
          dominated.
    \item On consumer Blackwell with our software-microscaled path,
          FP4's hardware throughput advantage is more than cancelled
          by the per-mma scaling overhead.
  \end{itemize}
  \begin{spoiler}
    This does \emph{not} contradict SageAttention3's positive FP4
    result. Their hardware path
    (\texttt{mxf4nvf4.m16n8k64}) internalises the per-element scale
    at the mma boundary. \textbf{The blocker is the layout, not the
    FP4 idea.}
  \end{spoiler}
\end{frame}

\begin{frame}[fragile]{Bonus: the SDPA dispatch is not what you think}
  \begin{block}{What we expected}
    PyTorch SDPA on RTX\,5080 dispatches to \textbf{FlashAttention-2 in
    FP16}. Beating it would mean beating a heavily-tuned FA-2 kernel.
  \end{block}
  \begin{whatbroke}
    The PyTorch\,2.9.1+cu128 wheel was compiled \emph{without} flash
    attention. cuDNN attention and memory-efficient attention are
    runtime-disabled for our \texttt{(sm\_120, FP16, non-causal)}
    inputs. SDPA falls through to the \textbf{MATH backend} -- a pair
    of cuBLAS matmuls with a softmax in between. It materialises the
    full $S$ and $P$.
  \end{whatbroke}
  Concretely, when we tried to pin the dispatch:
  \begin{lstlisting}
with torch.nn.attention.sdpa_kernel(SDPBackend.FLASH_ATTENTION):
    F.scaled_dot_product_attention(Q, K, V)  # raises NoBackendError
  \end{lstlisting}
  \begin{tldr}
    Comparing a custom kernel ``against SDPA'' without naming the
    dispatch is misleading. Always pin the backend; always disclose
    it.
  \end{tldr}
\end{frame}

\begin{frame}[fragile]{Tensor Cores are actually engaged: the SASS proof}
  Nsight Compute hardware counters require admin
  (\texttt{ERR\_NVGPUCTRPERM}); on a consumer card without admin we
  cannot use them. \textbf{So we read the SASS directly.}
  \vspace{0.4em}
  \begin{lstlisting}
cuobjdump --dump-sass kernels/v3_flash_fp8/_C.cp311-win_amd64.pyd `
    | Select-String QMMA | Measure-Object | % Count
# 96
  \end{lstlisting}
  \begin{center}
    \includegraphics[width=0.58\linewidth]{../paper/figures/fig_tensor_core_engagement.pdf}
  \end{center}
\end{frame}

\begin{frame}{Pareto summary}
  \begin{center}
    \includegraphics[width=0.78\linewidth]{../paper/figures/fig_pareto_main.pdf}
  \end{center}
  \begin{itemize}
    \item \textbf{V3 is the practical sweet spot} when an application
          can absorb $\sim 5\%$ relative L2 error.
    \item SDPA is faster but has a hidden cost (no fusion on this
          stack; full $S, P$ in HBM).
    \item V4 sits dominated by V3 in this software stack -- waiting
          for the hardware-microscaling path.
  \end{itemize}
\end{frame}

\section{Part 6: Why It Matters}

\begin{frame}{What you should take away}
  \begin{enumerate}
    \item \textbf{Algorithmic fusion is the biggest single win.} The
          $17\times$ memory reduction at V1\,$\to$\,V2 came from
          changing the structure, not the precision. Always pull the
          memory lever first.
    \item \textbf{Narrow precision pays off only when the layout is
          knowable.} The V2\,$\to$\,V3 latency win is roughly half FP8
          throughput, half register-resident O. Both required the
          fragment layout to be specified by the PTX ISA.
    \item \textbf{Lower precision is not strictly better.} FP4 lost on
          consumer Blackwell because the cheap-microscaling path is
          incompatible with the SMEM layout we share with the FP8
          kernel. \emph{Hardware quirks defeat ``obvious'' optimisations.}
    \item \textbf{Vendor baselines are moving targets.} The SDPA
          dispatch is build- and OS-dependent. Pin it, disclose it,
          measure it.
    \item \textbf{Read the SASS.} \texttt{cuobjdump} tells you exactly
          which Tensor-Core instructions you emitted -- more reliable
          than runtime metrics gated by admin permissions.
  \end{enumerate}
\end{frame}

\begin{frame}{What we left undone (and why)}
  \begin{itemize}
    \item \textbf{Hardware-microscaled NVFP4
          (\texttt{mxf4nvf4.m16n8k64}).} Would likely flip V4 vs V3.
          Requires a swizzled SMEM layout incompatible with V3's
          idiom; multi-week scope.
    \item \textbf{Backward pass.} Non-trivial for narrow precisions
          (Attn-QAT documents specific instabilities). Forward
          inference only here.
    \item \textbf{RTX\,5090 replication.} Same compute capability;
          very different SM count, memory bus, VRAM. Would tell us
          how much of the V4 result is hardware-microscaling-
          availability vs 5080-specific.
    \item \textbf{Backend pinning that actually works.} The SDPA
          \texttt{FLASH\_ATTENTION} pin failed on our build; on a
          Linux build with a flash-enabled wheel it would not. A
          one-day Linux re-run remains.
    \item \textbf{Production-grade tile tuning.} Our 64$\times$64
          tile is a defensible default; an autotuned sweep over tile
          sizes and warps-per-block is deferred.
  \end{itemize}
\end{frame}
